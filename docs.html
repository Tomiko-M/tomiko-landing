Documentation · v0.2.0

Everything tomiko can do.

tomiko records the real LLM traffic of your tests on the first run and replays it on every run after. This page covers every module, option, matcher, fault, command and type in version 0.2.

Testing code that calls a language model is awkward. Real API calls are slow and cost money, they need a key, and they return a slightly different answer every time. Mocking them by hand is tedious, and the mocks drift away from what the API really sends.

tomiko takes the approach of HTTP recorders such as VCR, nock or Polly, but it understands LLM traffic:

  • Record & replay. The first run sends real requests and writes them to a JSON cassette next to the test. Later runs answer from the file: no network, no tokens, a few milliseconds.
  • Streams replay exactly. Server-sent events are stored chunk by chunk and replayed the same way.
  • Behavioural assertions. Matchers read the cassette: which tools the model called, with which arguments, in which order, how many requests it took and what it cost. A model can judge what the answer means, once, and the verdict is replayed after.
  • Failures on demand. Rate limits, overloads, dropped connections and slow responses, and a model that calls a tool that doesn't exist, breaks its arguments, refuses or stops at the token limit.
  • Readable diffs. When a prompt changes, the failure shows the changed words. When a model changes, tomiko diff shows what it now does differently.
  • Safe to commit. Request headers are never stored, and a recording that holds an API key is never saved.
  • No dependencies. It works on fetch: Anthropic, OpenAI and Google SDKs, the Vercel AI SDK, LangChain.js, and anything else.

Quick start

Wrap a test in useCassette, run it once with a key, commit the cassette.

1. Write the test

import { expect, test } from "vitest";
import { useCassette } from "tomiko/vitest";
import { agent } from "./agent";

test("books a table", async () => {
  await useCassette(async (c) => {
    const answer = await agent.run("Table for two at 7pm, by the window");

    expect(answer).toContain("Booked");
    expect(c).toHaveCalledTool("book_table", { guests: 2 });
    expect(c).toCostLessThan(0.05);
  });
});

2. Record it once

ANTHROPIC_API_KEY=sk-ant-... npx vitest run

The requests go to the real API. tomiko saves every request and response to __cassettes__/booking.test.ts/books-a-table.json, next to the test file. Before saving, it checks the recording for secrets.

3. Commit and replay

git add __cassettes__
ANTHROPIC_API_KEY=test npx vitest run   # replays in milliseconds, offline

From now on the test replays the cassette. On CI (where CI is set) tomiko runs in replay mode and never touches the network: a request without a recording fails the test instead of calling the API.

⚠

SDKs refuse to build a request without an API key, before tomiko can answer it. When replaying, give them any value: ANTHROPIC_API_KEY=test. The key is never stored, and a replay never sends it.

Next

  • Check what the answer means with toMeet.
  • Test retries and bad answers with faults.
  • See every run as a conversation: npx tomiko view.
  • Print a cost summary after the suite: printSummary().

How it works

tomiko works at the fetch level. A cassette is a JSON file holding interactions: recorded requests with their responses. While a cassette is active, requests go through it:

  1. Open. The cassette resolves its mode and its file path, and loads the file if it exists. In record mode the old file is ignored.
  2. Activate. cassette(), useCassette() and setupCassettes() replace globalThis.fetch with tomiko's dispatcher. openCassette() doesn't touch globals: you pass c.fetch to your client.
  3. Intercept. Each request becomes a RecordedRequest: the method, the URL with secret query parameters redacted, and the parsed body. Requests rejected by intercept go straight to the network.
  4. API faults. Simulated failures that target this request answer it first. A failed request never reaches the network and is never recorded.
  5. Match. Outside record mode, tomiko looks for a recording with the same method, URL and body (see matching). If one matches, its response is replayed.
  6. Record or fail. With no match, auto and record send the request and record the response. replay throws a RequestMismatchError that shows the closest recording.
  7. Misbehave. If a model fault targets the request, your code gets the answer rewritten; the cassette keeps the real one.
  8. Close. tomiko restores fetch, waits for streams still recording, checks new recordings for secrets, applies redact, saves the file if anything new was recorded, and builds a report.

The response your code receives is a normal Response: the same status, the kept headers, the same body. Streams arrive chunk by chunk, so SDKs can't tell a replay from the real API.

Using with Vitest

Import from tomiko/vitest. Importing it also registers the matchers on expect, with their types (Vitest 5).

One cassette per test: useCassette

import { useCassette } from "tomiko/vitest";

describe("booking agent", () => {
  test("books a window table", async () => {
    await useCassette(async (c) => {
      await agent.run("Window table for two at 7pm");
      expect(c).toHaveCalledTool("book_table");
    });
  });
});

The cassette is named after the test, like a Vitest snapshot. Each describe block becomes a directory:

test/booking.test.ts
test/__cassettes__/booking.test.ts/booking-agent/books-a-window-table.json

The function's return value is passed through: const answer = await useCassette(() => agent.run(...)).

Several cassettes in one test

test("remembers the conversation", async () => {
  await useCassette("first turn", () => chat.send("My name is Ana"));
  await useCassette("second turn", async (c) => {
    const reply = await chat.send("What is my name?");
    expect(reply).toMatch(/Ana/);
  });
});
// → remembers-the-conversation/first-turn.json
// → remembers-the-conversation/second-turn.json

Every test gets a cassette: setupCassettes

To give every test a cassette without wrapping each one, call setupCassettes() in a setup file. It registers a beforeEach that opens and activates a cassette named after the test, and an afterEach that closes it.

import { configure } from "tomiko";
import { setupCassettes } from "tomiko/vitest";

configure({ ignore: ["metadata.user_id"] }); // optional defaults
setupCassettes();
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { setupFiles: ["./vitest.setup.ts"] },
});

Then read the current cassette in a test with currentCassette():

import { currentCassette } from "tomiko/vitest";

test("searches before booking", async () => {
  await agent.run("Table for two");
  expect(currentCassette()).toHaveCalledToolsInOrder(["search_tables", "book_table"]);
});
  • A test that makes no requests leaves no file behind.
  • Call setupCassettes() inside a describe block to cover only that block.
  • It takes the same options, merged over the configure() defaults.
  • Don't use useCassette() inside a test that setupCassettes() already covers: cassettes don't nest.

Names are made safe for the file system: characters other than letters (in any script), digits, _, . and - become -, so "books a table" becomes books-a-table. A / inside a test name becomes -, and .. can't escape the directory. The CLI commands rely on this layout to tell which test file a cassette belongs to.

Concurrency

⚠

useCassette() and setupCassettes() patch the global fetch, and only one cassette can be active at a time, so they don't work with test.concurrent. Vitest's default parallelism across files is fine: each test file runs in its own worker.

For concurrent code inside one test, use openCassette() and give each client its own c.fetch.

Matcher types on older Vitest

The types are declared for Vitest 5. On older versions, declare them yourself with the exported TomikoMatchers interface, following your version's custom matcher docs:

import type { TomikoMatchers } from "tomiko";

declare module "vitest" {
  interface Assertion<T = any> extends TomikoMatchers<T> {}
}

Jest & other runners

The core tomiko entry has no test runner dependency. It works in Jest, node:test, Mocha, a plain script, or any other runner. The CLI commands that run tests (record, matrix, prune) use Vitest or Jest, whichever the nearest package.json lists, or npm test; give your own command after --.

cassette(name, fn)

import { cassette } from "tomiko";

const answer = await cassette("support/refund", async (c) => {
  return agent.run("I want a refund");
});
// → __cassettes__/support/refund.json (relative to the working directory)

While fn runs, globalThis.fetch goes through the cassette. Then fetch is restored and new recordings are saved. Slashes in the name create subdirectories.

Jest

import { matchers, type TomikoMatchers } from "tomiko";

expect.extend(matchers);

declare global {
  namespace jest {
    interface Matchers<R> extends TomikoMatchers<R> {}
  }
}
import { cassette } from "tomiko";

test("refunds a damaged order", async () => {
  await cassette("refund/damaged-order", async (c) => {
    const answer = await agent.run("My order arrived broken");
    expect(c).toHaveCalledTool("issue_refund");
    await expect(answer).toMeet("apologizes and confirms the refund");
  });
});

Use the Node test environment (testEnvironment: "node"), which has the global fetch.

node:test

import { test } from "node:test";
import assert from "node:assert/strict";
import { cassette, judge } from "tomiko";

test("answers opening hours", async () => {
  await cassette("faq/opening-hours", async (c) => {
    const answer = await agent.run("When do you open?");
    assert.equal(c.calls.length, 1);
    const verdict = await judge(answer, "gives the opening time");
    assert.ok(verdict.pass, verdict.reason);
  });
});

Clients created before a test

The Anthropic and OpenAI SDKs capture fetch when a client is constructed. A client built inside a test picks up tomiko automatically. A client built once at module load captured the real fetch before any cassette existed, so give it tomiko's:

import Anthropic from "@anthropic-ai/sdk";
import OpenAI from "openai";
import { fetch } from "tomiko";

export const anthropic = new Anthropic({ fetch });
export const openai = new OpenAI({ fetch });

tomiko's fetch sends each call to whichever cassette is active at that moment, and to the real network when none is. It's safe to leave in production code.

Anthropic SDK

import Anthropic from "@anthropic-ai/sdk";

await useCassette(async (c) => {
  const client = new Anthropic(); // created inside: nothing to configure
  const stream = client.messages.stream({ model: "claude-opus-5-5", max_tokens: 512, messages });
  const message = await stream.finalMessage();
});

OpenAI SDK

import OpenAI from "openai";

await useCassette(async (c) => {
  const client = new OpenAI();
  await client.responses.create({ model: "gpt-5.4", input: "Hi" });
  expect(c).toHaveUsedModel("gpt-5.4");
});

Google Gemini 0.2

Gemini works end to end: usage with cached and thinking tokens, function calls, streaming, stop reasons, simulated errors in Gemini's format, the viewer and diffs. Tested with @google/genai and the AI SDK's Google provider.

import { GoogleGenAI } from "@google/genai";

await useCassette(async (c) => {
  const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });
  await ai.models.generateContent({ model: "gemini-3.5-flash", contents: "Weather in Faro?", config: { tools } });
  expect(c).toHaveCalledTool("get_weather", { city: "Faro" });
});

The AI SDK invents new function-call ids for Gemini on every run; tomiko ignores them when matching, so tool loops replay.

Vercel AI SDK

The AI SDK looks up globalThis.fetch on every request, so even a provider created at module load works without setup:

import { createAnthropic } from "@ai-sdk/anthropic";
import { generateText, stepCountIs } from "ai";

const anthropic = createAnthropic();

test("plans a trip with tools", async () => {
  await useCassette(async (c) => {
    await generateText({
      model: anthropic("claude-opus-5-5"),
      tools: { getWeather },
      stopWhen: stepCountIs(5),
      prompt: "Weather in Faro?",
    });
    expect(c).toHaveCalledTool("getWeather", { city: "Faro" });
  });
});

LangChain.js

LangChain builds its SDK client lazily and caches it. A client built during a test keeps working in later tests, because tomiko's global fetch routes to the cassette active at call time. If the model may be called before any test, pass fetch explicitly:

import { ChatAnthropic } from "@langchain/anthropic";
import { ChatOpenAI } from "@langchain/openai";
import { fetch } from "tomiko";

const claude = new ChatAnthropic({ model: "claude-opus-5-5", clientOptions: { fetch } });
const gpt = new ChatOpenAI({ model: "gpt-5.4", configuration: { fetch } });

Plain fetch and other APIs

Any fetch call is recorded, LLM or not. JSON, text, SSE and binary bodies are all supported. To record only some hosts, use intercept:

await cassette("weather", run, {
  intercept: (request) => new URL(request.url).hostname === "api.anthropic.com",
});

Provider detection

tomiko detects the provider to choose error formats for faults, and to read usage, stop reasons and tool calls. It checks, in order: the anthropic-version request header; a host ending in anthropic.com, openai.com or generativelanguage.googleapis.com; a path ending in /v1/messages (Anthropic) or /chat/completions / /responses (OpenAI). That last check makes proxies and gateways with a custom base URL work too.

Modes & CI

How the mode is chosen

  1. The TOMIKO_MODE environment variable, if set. It wins over everything, so a whole suite can be re-recorded without code changes.
  2. The mode option, from the cassette call or from configure().
  3. replay when CI is set to anything other than empty, 0 or false.
  4. Otherwise auto.

A cassette named in TOMIKO_RECORD is re-recorded whatever the mode. That's how tomiko record re-records a few cassettes while the rest replay.

npx tomiko record                       # re-record everything, cost estimate first
TOMIKO_MODE=record npx vitest run       # the same, without the estimate and the diff
TOMIKO_RECORD=test/__cassettes__/agent.test.ts npx vitest run   # just these
CI=1 npx vitest run                     # check locally that CI will pass

Details

  • A missing cassette fails only when needed. In replay mode with no file, the test fails with CassetteNotFoundError only when it sends a request. Tests without LLM calls pass.
  • Repeated requests. Identical requests are answered in the order they were recorded. When they run out, auto records a new one and replay repeats the last.
  • auto appends. New recordings are added to the existing file, so adding a step to an agent records only the new step.
  • record replaces. The old file is not loaded. After the run the file holds only this run's interactions.

Transient errors are not saved

While recording, responses with status 408, 429 or 5xx are passed to your code but not saved, with a warning in the report: a recorded outage would replay forever. The SDK's retry is what gets recorded. To keep them, set recordErrors: true, or better, simulate them with faults.

- run: npm ci
- run: npm test

    ANTHROPIC_API_KEY: test   # SDKs need some key; replay never sends it

Request matching

A live request matches a recording when all of these are equal:

  • the HTTP method;
  • the URL, after secret query parameters are redacted;
  • the body, compared as canonical JSON: object key order doesn't matter, array order does. Paths listed in ignore are removed first, and secrets the guard replaced with placeholders are replaced in the live request the same way.

Headers are not compared and not stored. In Gemini requests, the ids of functionCall and functionResponse parts are left out of matching too, because the AI SDK invents new ones on every run.

Ignoring volatile fields: ignore

Leave out parts of the body that change between runs. Paths are dot-separated, and * matches any key or array index:

configure({
  ignore: [
    "metadata.user_id",            // one field
    "messages.*.cache_control",    // the field in every message
    "tools.*.input_schema.description",
  ],
});

When nothing matches

In replay mode, a request with no recording throws RequestMismatchError. tomiko finds the most similar recording for the same method and URL, preferring ones not yet used in this run, and prints a leaf-by-leaf diff:

RequestMismatchError: No recorded interaction in cassette "agent/booking" matches POST https://api.anthropic.com/v1/messages.
Closest recording (94% similar) differs in:
  ~ system: "…for a small restaurant. [-Always-]{+Never+} confirm the time and…"
  + temperature: 0.2
  - metadata.user_id: "u_123"

If the change is intentional, re-record with TOMIKO_MODE=record, or allow near matches with the `fuzzy` option.
MarkMeaning
~changed. For strings, only the changed words are shown, as [-old-]{+new+} with a few words of context.
+present in the live request only
-present in the recording only

Up to 12 differences are shown, and values are clipped at 120 characters. If nothing was ever recorded for that endpoint, the error says so instead. To find which cassettes no longer match without reading errors one by one, run npx tomiko record --stale.

Near matches: fuzzy

With fuzzy: 0.9, a request at least 90% similar to a recording replays it, and the diff becomes a warning in the report. Useful while you iterate on prompt wording.

  • Similarity is computed per JSON leaf and weighted by length, so a one-word edit in a long prompt barely moves the score, while a changed model name or tool does.
  • Strings are compared word by word (a Dice coefficient over words).
  • A recording from a different model is never used, however similar the prompt.
  • The value must be in (0, 1], or false (the default) to turn it off.

Streaming

Responses with content-type: text/event-stream are recorded as a list of chunks, exactly as they arrived, and replayed chunk by chunk. stream(), finalMessage(), for await loops, streamText and streamed tool calls behave as they did live.

  • Recorded while you read. tomiko passes the stream through to your code and copies each chunk as it's read. Your code sees the same bytes in the same chunks.
  • Stopping early is fine. If your code stops reading, or never reads, the recording isn't cut short: close() drains the rest before saving.
  • Failed streams aren't saved. A stream that fails while recording would replay truncated, so it's left out of the cassette and a warning is added to the report.
  • Secrets across events. A key the model spelled out over several streamed events is found by the secrets guard too.
  • Usage and tool calls are reassembled from the events: Anthropic message_start / message_delta / input_json_delta, OpenAI Chat delta.tool_calls, the Responses API's response.completed, and Gemini's streamed candidates.

To test a stream that breaks mid-way, use fault.cutStream(). Model faults also work on streams: the rewritten answer is streamed in the provider's own event format.

Behaviour matchers

The matchers read the requests and responses the cassette served in this run, recorded or replayed. They work on any cassette: the one passed to your callback, currentCassette(), or one from openCassette().

expect(c).toHaveCalledTool("book_table", { guests: 2, table: expect.any(Number) });
expect(c).toHaveCalledToolTimes("search_tables", 1);
expect(c).toHaveCalledToolsInOrder(["search_tables", "book_table"]);
expect(c).not.toHaveCalledTool("cancel_booking");
expect(c).toHaveMadeRequests({ max: 5 });       // no runaway loops
expect(c).toHaveUsedModel(/claude-opus/);
expect(c).toCostLessThan(0.05);
expect(c).toHaveUsedFewerTokensThan(20_000);
await expect(answer).toMeet("confirms the booking for two at 7pm");
MatcherPasses when
toHaveCalledTool(name, input?)the model called the tool at least once. With input, at least one call's arguments must contain it.
toHaveCalledToolTimes(name, n)the tool was called exactly n times
toHaveCalledToolsInOrder(names)the tools were called in this relative order; other calls may come in between
toHaveMadeRequests(n | { min, max })the number of requests is exactly n, or within the range (either bound optional)
toHaveUsedModel(model | RegExp)at least one request used this model
toCostLessThan(usd)the estimated cost is strictly below usd
toHaveUsedFewerTokensThan(n)input, output, cache read and cache write tokens add up to fewer than n
toMeet(criteria, options?) 0.2a judge model finds the text, or the cassette's last answer, meets criteria. Asynchronous: await it. See Judging answers.

How input is compared

For toHaveCalledTool, the expected input is matched as a subset: every key you give must be in the arguments with a matching value, and nested plain objects are compared the same way. Other values, arrays included, use your runner's equality, so asymmetric matchers work:

expect(c).toHaveCalledTool("search", { query: expect.stringMatching(/lisbon/i) });
expect(c).toHaveCalledTool("book_table", { guest: { name: "Ana" } }); // other keys allowed
expect(c).toHaveCalledTool("tag", { labels: ["vip", "window"] });     // the array must be equal

Failure messages

When a tool matcher fails, it lists what the agent did instead, with arguments shortened to 80 characters:

expected cassette "booking.test.ts/books a table" to call tool "cancel_booking".
Tool calls:
  search_tables({"time":"19:00","guests":2})
  book_table({"table":12,"guests":2,"note":"window"})

What counts

  • Tool calls are read from Anthropic tool_use, server_tool_use and mcp_tool_use blocks, OpenAI Chat Completions tool_calls, Responses API function_call items and Gemini functionCall parts, in plain and streamed responses. Arguments streamed in fragments are reassembled.
  • Requests include every request your code made: retries and requests hit by a fault count too.
  • The judge's requests never count: not in tool calls, request counts, tokens or cost.
  • A model fault is seen as your code saw it: the rewritten answer, not the recorded one.
  • toCostLessThan throws if a request has usage but no known price, instead of counting it as free. Add the model with the pricing option.

Custom assertions with c.calls

For anything the matchers don't cover, read the data. c.calls is a list of RecordedCall, one per request, in order. c.toolCalls is every tool call across them.

await useCassette(async (c) => {
  await agent.run("Table for two");

  const last = c.calls.at(-1)!;
  expect(last.text).toMatch(/booked/i);              // the final answer
  expect(last.requestBody.system).toContain("restaurant");
  expect(c.calls.every((call) => call.status === 200)).toBe(true);
  expect(c.toolCalls.map((t) => t.name)).toEqual(["search_tables", "book_table"]);
});

Judging answers 0.2

Some answers can't be checked with toContain: that the agent apologizes, offers what the policy allows, stays polite. toMeet has a model judge the answer against criteria in plain words:

test("handles a late order", async () => {
  await useCassette(async () => {
    const answer = await agent.run("My order is two weeks late");

    await expect(answer).toMeet("apologizes and offers a refund");
  });
});

API failures

Live APIs rarely fail on cue. Faults let you test retry and error handling deterministically, on top of a normal recording:

import { fault } from "tomiko";

// 429, 429, then the recording
await useCassette(run, { faults: [fault.rateLimit({ times: 2 })] });

// the connection drops mid-stream
await useCassette(run, { faults: [fault.cutStream({ afterEvents: 3 })] });

A failed request never reaches the network and is never recorded. Error responses use each provider's real format, so SDKs throw their usual typed errors (RateLimitError, InternalServerError, …) and retry as they would in production.

Choosing which requests are hit

Every factory, model faults included, accepts targeting options (FaultTarget):

OptionEffect
timeshit the first times requests that when accepts. Default 1; Infinity hits all of them.

fault.networkError({ when: (r) => r.url.includes("/v1/messages") });

Combining faults

Pass several faults in the array; each keeps its own hit count. On one request, latency delays add up and apply first. Then the first failing fault in declaration order (rateLimit, overloaded, serverError or networkError) answers the request. Otherwise the request is served, a model fault rewrites the answer, and cutStream cuts what's served.

Secrets guard 0.2

Cassettes get committed, so a key that ends up in one gets published. Keys find their way in more often than you'd think: an agent reads a .env file with a tool, a prompt includes a config, a model repeats what it was given.

tomiko checks every recording before it saves it. When it finds a secret, it saves nothing and fails the test, saying where the secret is but never printing it:

SecretsFoundError: Cassette "agent.test.ts/reads the config" was not saved: it contains 1 secret.

  ● Anthropic API key  sk-ant-api03-…f9Qa  your $ANTHROPIC_API_KEY
    #2 request body › messages[3].content[0].content

Nothing was written to __cassettes__/agent.test.ts/reads-the-config.json. To save it:
  · secrets: "redact"           replaces each one with a placeholder; replays still match
  · redact: (interaction) => …  scrubs them yourself before saving
  · secrets: { allow: [...] }   for values that are not real secrets

What it finds

  • 20 key formats: Anthropic, OpenAI, OpenRouter, Google, Groq, xAI, Hugging Face, Replicate, Perplexity, GitHub, GitLab, Slack tokens and webhooks, Stripe, AWS access key ids, npm, SendGrid, private keys, JSON Web Tokens, bearer tokens, and passwords in URLs.
  • Your own secrets: the values of environment variables named like secrets (*_API_KEY, *_TOKEN, *_SECRET, *_PASSWORD), whatever their format.
  • Named fields: values of fields such as password or client_secret.
  • Across streamed events: a key the model spelled out in pieces is found too.

Placeholders such as sk-ant-xxxx, <your key> or …EXAMPLE, and well-known documentation examples, are not flagged.

What happens

secretsA recording with a secret in it
"fail" (default)is not saved, and the test fails with where each secret is (SecretsFoundError)
"redact"is saved with each secret replaced by a placeholder such as [REDACTED:anthropic-api-key]; the value of an environment variable becomes [REDACTED:$NAME]
"warn"is saved as is, with a warning in the report

A redacted request still matches: tomiko replaces the same secrets in the live request before comparing. A cassette recorded before the check, or with it off, gets a warning when it's replayed, pointing to npx tomiko scan --fix.

Scrubbing personal data: redact

Bodies hold whatever your prompts and the model's answers hold, which may include personal data. redact receives each interaction just before it is written and returns the version to save:

const EMAIL = /[\w.+-]+@[\w-]+\.[\w.]+/g;

configure({
  redact: (interaction) => {
    const scrub = (v: unknown) => JSON.parse(JSON.stringify(v).replace(EMAIL, "user@example.com"));
    interaction.request.body = scrub(interaction.request.body);
    interaction.response.body = scrub(interaction.response.body);
    return interaction;
  },
});
  • It receives a deep copy, so you can change it in place. Your test still sees the real values during this run.
  • It runs on every interaction in the file on each save, including ones recorded earlier, so it should give the same result when applied twice.
  • Redacted values are what later runs match against. If you rewrite part of the request, replay will see a different body; prefer ignore for request fields that only need to be left out of matching.

Put a budget on every test

import { afterEach, expect } from "vitest";
import { currentCassette, setupCassettes } from "tomiko/vitest";

setupCassettes();
afterEach(() => {
  expect(currentCassette()).toCostLessThan(0.10);
});

With Vitest's default sequence.hooks: "stack", after-hooks run in reverse order of registration, so this one runs before the one from setupCassettes() closes the cassette.

Check tone and policy with a judge

await useCassette(async () => {
  const answer = await agent.run("This is the third time my order is late!!");
  await expect(answer).toMeet("stays calm, apologizes once, and does not promise a date it can't keep");
  await expect(answer).not.toMeet("blames the customer");
});

Judge inside the cassette, so the verdicts are recorded too. Outside one, every run asks the model again.

Make an agent survive a bad model

for (const f of [fault.hallucinatedTool(), fault.brokenArguments(), fault.emptyAnswer()]) {
  test(`recovers from ${f.name}`, async () => {
    await useCassette(f.name, async (c) => {
      const answer = await agent.run("Weather in Lisbon?");
      await expect(answer).toMeet("gives the weather in Lisbon");
      expect(c).toHaveMadeRequests({ max: 4 });
    }, { faults: [{ ...f, on: 1 }] });
  });
}

Run it once with a key in auto mode: the recovery path is recorded, then replayed.

Prompts with dates or random ids

A prompt with today's date never matches yesterday's recording, and tomiko doctor will flag it as never cached. Move the date into the user's message, freeze it in tests (vi.setSystemTime()), or leave the field out of matching with ignore.

Iterate on a prompt without re-recording each time

await useCassette(run, { fuzzy: 0.9 }); // small wording changes replay, with a warning

Once the wording settles, re-record with npx tomiko record --stale and remove fuzzy.

Troubleshooting

“Could not resolve authentication method”

The Anthropic SDK (and the OpenAI SDK, with its own message) throws this before sending the request when no API key is set, so tomiko never sees the request. When replaying, set any value: ANTHROPIC_API_KEY=test.

Requests go to the real API instead of the cassette

The client captured fetch before the cassette was active, usually because it was created at module load. Pass fetch from tomiko: new Anthropic({ fetch }).

CassetteNotFoundError on CI

The test sent a request, but its cassette was never recorded or never committed. Run the test locally once, then commit __cassettes__/. Check that .gitignore doesn't exclude it, and that the recording wasn't refused by the secrets guard.

RequestMismatchError after changing a prompt

The recording no longer reflects your code, and the diff shows what changed. Re-record with npx tomiko record --stale, or allow near matches with fuzzy. If the difference is a volatile field, add it to ignore.

SecretsFoundError but the value isn't a secret

Allow it: configure({ secrets: { allow: ["sk-test-fixture-key"] } }), or --allow for tomiko scan. If it is a real key, the error is the guard doing its job: keep it out of the prompt or tool result, or save with secrets: "redact".

The judge fails with 401 or 403

Recording a verdict needs the judge provider's key: ANTHROPIC_API_KEY for the default claude-haiku-5-5, OPENAI_API_KEY or GEMINI_API_KEY for others. Replaying a recorded verdict needs none.

An error response isn't in the cassette

Transient errors (408, 429, 5xx) are passed through while recording but not saved, so an outage can't replay forever. Set recordErrors: true to keep them, or simulate them with faults.

No price, or a different price than before

Since 0.2 a pricing key only matches snapshots of its model, so a different model (such as gpt-5.6) no longer borrows a shorter key's price. Add it with pricing. toCostLessThan refuses to count unknown models as free.

NestedCassetteError

Two cassettes were active at once: useCassette() inside a test already covered by setupCassettes(), a cassette() inside another, or concurrent tests. Use one at a time, or openCassette() for concurrent work.

Recording works, but replay gives different results

Something else in your code isn't deterministic: the current time, random numbers, or parallel requests whose order differs between runs. Freeze time and seeds in tests.

Matchers don't type-check

Import tomiko/vitest in the test or the setup file so the type augmentation loads. On Vitest older than 5, or on Jest, declare the types yourself: see Vitest and Jest.

Still stuck?

Open an issue on GitHub with the error and, if possible, the cassette. Run npx tomiko scan on it first.

Find the cheapest model that passes: tomiko matrix

  • Runs your tests on each model against the live API, every request sent to it instead of the model in your code.
  • Estimates the cost from your current recordings and asks before spending anything; --yes, --max-cost.
  • Lays the models side by side with what you use now: tests passed, cost of a run and how many times less, time, and in how many cassettes the model behaves differently.
  • Ends with a verdict: the cheapest model that passes every test, or that nothing cheaper does.
  • Your cassettes are left alone; --keep saves each model's to .tomiko/matrix/<model>.

Find where you overpay: tomiko doctor

  • A system prompt that changes between requests, so the prompt cache never hits, with the part that changes.
  • Tools offered and never called; huge tool results sent back on every turn; the same request sent twice; max_tokens far above what answers use.
  • Each finding says what it costs a run; the total counts shared tokens once. --json, and diagnose() from code.

Assert what the answer means: toMeet

  • A model judges the output against your criteria; on failure you get its reason and the output.
  • The judge's request and verdict are recorded in the cassette, so every run after replays it: offline, free, the same every time.
  • claude-haiku-5-5 by default; any Anthropic, OpenAI or Gemini model with { model } or configure({ judge }).

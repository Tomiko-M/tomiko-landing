Documentation · v0.1

Everything tomiko can do.

tomiko records the real LLM traffic of your tests on the first run and replays it on every run after. This page covers every module, option, matcher, fault, type and command.

Testing code that calls a language model is awkward: real API calls are slow, cost money, need a key, and return a slightly different answer every time. Mocking them by hand is tedious and drifts away from what the API really sends.

tomiko takes the approach of HTTP recorders such as VCR, nock or Polly, but it understands LLM traffic:

  • Record & replay. The first run sends real requests and writes them to a JSON cassette next to the test. Later runs answer from the file: no network, no key, no tokens, a few milliseconds.
  • Streams replay exactly. Server-sent events are stored chunk by chunk and replayed the same way, so streaming SDK helpers behave as they did live.
  • Behavioural assertions. Matchers read the cassette: which tools the model called, with which arguments, in which order, how many requests it took and what it cost.
  • Failures on demand. Rate limits, overloads, server errors, dropped connections, cut streams and latency, in each provider's real error format.
  • Readable diffs. When a prompt changes, the failure shows the changed words.
  • Safe to commit. Request headers, and with them API keys, are never written to disk.
  • No dependencies. It works on fetch, so it supports the Anthropic and OpenAI SDKs, the Vercel AI SDK, LangChain.js and anything else built on fetch.

Quick start

Wrap a test in useCassette, run it once with a key, commit the cassette.

1. Write the test

import { expect, test } from "vitest";
import { useCassette } from "tomiko/vitest";
import { agent } from "./agent";

test("books a table", async () => {
  await useCassette(async (c) => {
    const answer = await agent.run("Table for two at 7pm, by the window");

    expect(answer).toContain("Booked");
    expect(c).toHaveCalledTool("book_table", { guests: 2 });
    expect(c).toCostLessThan(0.05);
  });
});

2. Record it once

ANTHROPIC_API_KEY=sk-ant-... npx vitest run

The requests go to the real API. tomiko saves every request and response to __cassettes__/booking.test.ts/books-a-table.json, next to the test file.

3. Commit and replay

git add __cassettes__
ANTHROPIC_API_KEY=dummy npx vitest run   # replays in milliseconds, offline

From now on the test replays the cassette. On CI (where CI is set) tomiko runs in replay mode and never touches the network: a request without a recording fails the test instead of calling the API.

⚠

The Anthropic and OpenAI SDKs refuse to build a request without an API key, before tomiko can answer it. When replaying, set any value: ANTHROPIC_API_KEY=dummy. See Troubleshooting.

How it works

tomiko works at the fetch level. A cassette is a JSON file holding interactions, each a recorded request with its response. While a cassette is active, requests go through it:

  1. Open. The cassette resolves its mode and its file path, and loads the file if it exists. In record mode the old file is ignored.
  2. Activate. cassette(), useCassette() and setupCassettes() replace globalThis.fetch with tomiko's dispatcher. openCassette() doesn't touch globals: you pass c.fetch to your client yourself.
  3. Intercept. Each request becomes a RecordedRequest: method, URL with secret query parameters redacted, and parsed JSON body. Requests rejected by intercept go straight to the network.
  4. Faults. Any simulated failures that target this request apply first. A faulted request never reaches the network and is never recorded.
  5. Match. Outside record mode, tomiko looks for a recording with the same method, URL and body (see matching). If one matches, its response is replayed.
  6. Record or fail. With no match, auto and record modes send the request to the network and record the response. replay mode throws a RequestMismatchError showing the closest recording.
  7. Close. tomiko restores fetch, waits for streams still recording, applies redact, saves the file if anything new was recorded, and builds a report.

The response your code receives is a normal Response: same status, the kept headers, the same body. Streams arrive chunk by chunk, so SDKs cannot tell a replay from the real API.

Using with Vitest

Import from tomiko/vitest. Importing it also registers the matchers on expect, with their types (Vitest 5).

One cassette per test: useCassette

import { useCassette } from "tomiko/vitest";

describe("booking agent", () => {
  test("books a window table", async () => {
    await useCassette(async (c) => {
      await agent.run("Window table for two at 7pm");
      expect(c).toHaveCalledTool("book_table");
    });
  });
});

The cassette is named after the test, like a Vitest snapshot. Each describe block becomes a directory:

test/booking.test.ts
test/__cassettes__/booking.test.ts/booking-agent/books-a-window-table.json

The function's return value is passed through: const answer = await useCassette(() => agent.run(...)).

Several cassettes in one test

Pass a suffix as the first argument. Each call gets its own file:

test("remembers the conversation", async () => {
  await useCassette("first turn", () => chat.send("My name is Ana"));
  await useCassette("second turn", async (c) => {
    const reply = await chat.send("What is my name?");
    expect(reply).toMatch(/Ana/);
  });
});
// → remembers-the-conversation/first-turn.json
// → remembers-the-conversation/second-turn.json

Every test gets a cassette: setupCassettes

To give every test a cassette without wrapping each one, call setupCassettes() in a setup file. It registers a beforeEach that opens and activates a cassette named after the test, and an afterEach that closes it.

import { configure } from "tomiko";
import { setupCassettes } from "tomiko/vitest";

configure({ ignore: ["metadata.user_id"] }); // optional defaults
setupCassettes();
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { setupFiles: ["./vitest.setup.ts"] },
});

Then read the current cassette in a test with currentCassette():

import { currentCassette } from "tomiko/vitest";

test("searches before booking", async () => {
  await agent.run("Table for two");
  expect(currentCassette()).toHaveCalledToolsInOrder(["search_tables", "book_table"]);
});
  • A test that makes no requests leaves no file behind.
  • Call setupCassettes() inside a describe block to cover only that block.
  • It takes the same options, merged over configure() defaults.
  • Don't use useCassette() inside a test that setupCassettes() already covers: cassettes don't nest.

Where cassettes live

SetupPath
default<test dir>/__cassettes__/<test file>/<describe…>/<test>.json
dir option set<dir>/<test file path relative to cwd>/<describe…>/<test>.json

Names are made safe for the file system: characters other than letters (in any script), digits, _, . and - become -, so "books a table" becomes books-a-table. A / inside a test name becomes -, and .. can't escape the directory.

Concurrency

⚠

useCassette() and setupCassettes() patch the global fetch, and only one cassette can be active at a time, so they don't work with test.concurrent. Vitest's default parallelism across files is fine: each test file runs in its own worker.

For concurrent code inside one test, use openCassette() and give each client its own c.fetch.

Matcher types on older Vitest

The types are declared for Vitest 5. On older versions, add the declaration yourself using the exported TomikoMatchers interface, following your version's custom matcher docs. For example:

import type { TomikoMatchers } from "tomiko";

declare module "vitest" {
  interface Assertion<T = any> extends TomikoMatchers<T> {}
}

Jest & other runners

The core tomiko entry has no test runner dependency. It works in Jest, node:test, Mocha, a plain script, or any other runner.

cassette(name, fn)

import { cassette } from "tomiko";

const answer = await cassette("support/refund", async (c) => {
  return agent.run("I want a refund");
});
// → __cassettes__/support/refund.json (relative to the working directory)

While fn runs, globalThis.fetch goes through the cassette. Then fetch is restored and new recordings are saved. Slashes in the name create subdirectories.

Jest

Register the matchers yourself, in a setup file:

import { matchers, type TomikoMatchers } from "tomiko";

expect.extend(matchers);

declare global {
  namespace jest {
    interface Matchers<R> extends TomikoMatchers<R> {}
  }
}
import { cassette } from "tomiko";

test("refunds a damaged order", async () => {
  await cassette("refund/damaged-order", async (c) => {
    await agent.run("My order arrived broken");
    expect(c).toHaveCalledTool("issue_refund");
  });
});

Use the Node test environment (testEnvironment: "node"), which has the global fetch.

node:test

import { test } from "node:test";
import assert from "node:assert/strict";
import { cassette } from "tomiko";

test("answers opening hours", async () => {
  await cassette("faq/opening-hours", async (c) => {
    const answer = await agent.run("When do you open?");
    assert.match(answer, /9/);
    assert.equal(c.calls.length, 1);
  });
});

Clients created before a test

The Anthropic and OpenAI SDKs capture fetch when a client is constructed. A client built inside a test picks up tomiko automatically. A client built once at module load captured the real fetch before any cassette existed, so give it tomiko's:

import Anthropic from "@anthropic-ai/sdk";
import OpenAI from "openai";
import { fetch } from "tomiko";

export const anthropic = new Anthropic({ fetch });
export const openai = new OpenAI({ fetch });

tomiko's fetch sends each call to whichever cassette is active at that moment, and to the real network when none is. It is safe to leave in production code.

Anthropic SDK

import Anthropic from "@anthropic-ai/sdk";

await useCassette(async (c) => {
  const client = new Anthropic(); // created inside: nothing to configure
  const stream = client.messages.stream({ model: "claude-opus-5-5", max_tokens: 512, messages });
  const message = await stream.finalMessage();
});

OpenAI SDK

import OpenAI from "openai";

await useCassette(async (c) => {
  const client = new OpenAI();
  const res = await client.responses.create({ model: "gpt-5", input: "Hi" });
  expect(c).toHaveUsedModel("gpt-5");
});
ℹ

The built-in price table only has Anthropic models. To use toCostLessThan with OpenAI or other providers, add their prices with the pricing option.

Vercel AI SDK

The AI SDK looks up globalThis.fetch on every request, so even a provider created at module load works without setup:

import { createAnthropic } from "@ai-sdk/anthropic";
import { generateText, stepCountIs, tool } from "ai";

const anthropic = createAnthropic();

test("plans a trip with tools", async () => {
  await useCassette(async (c) => {
    await generateText({
      model: anthropic("claude-opus-5-5"),
      tools: { getWeather },
      stopWhen: stepCountIs(5),
      prompt: "Weather in Faro?",
    });
    expect(c).toHaveCalledTool("getWeather", { city: "Faro" });
  });
});

LangChain.js

LangChain builds its SDK client lazily and caches it. A client built during a test keeps working in later tests because tomiko's global fetch routes to the cassette active at call time. If the model may be called before any test, pass fetch explicitly:

import { ChatAnthropic } from "@langchain/anthropic";
import { ChatOpenAI } from "@langchain/openai";
import { fetch } from "tomiko";

const claude = new ChatAnthropic({ model: "claude-opus-5-5", clientOptions: { fetch } });
const gpt = new ChatOpenAI({ model: "gpt-5", configuration: { fetch } });

Plain fetch and other APIs

Any fetch call is recorded, LLM or not. JSON, text, SSE and binary bodies are all supported. To record only some hosts, use intercept:

await cassette("weather", run, {
  intercept: (request) => new URL(request.url).hostname === "api.anthropic.com",
});

Provider detection

tomiko detects the provider to choose error formats for faults, and to read usage and tool calls. It checks, in order: the anthropic-version request header; a host ending in anthropic.com, openai.com or generativelanguage.googleapis.com; a path ending in /v1/messages (Anthropic) or /chat/completions / /responses (OpenAI). That last check makes proxies and gateways with a custom base URL work too.

Modes & CI

ModeA recording matchesNo recording matchesDefault when
autoreplayedsent to the API and recordedrunning locally
replayreplayedthe test fails, nothing is sentCI is set
recordignoredeverything is re-recordednever

How the mode is chosen

  1. The TOMIKO_MODE environment variable, if set. It wins over everything, so a whole suite can be re-recorded without code changes.
  2. The mode option, from the cassette call or from configure().
  3. replay when CI is set to anything other than empty, 0 or false.
  4. Otherwise auto.

The value is case-insensitive. An unknown mode throws TomikoError.

TOMIKO_MODE=record npx vitest run                   # refresh every cassette
TOMIKO_MODE=record npx vitest run -t "books a table" # refresh one test
CI=1 npx vitest run                                  # check locally that CI will pass

Details

  • A missing cassette fails only when needed. In replay mode with no file, the test fails with CassetteNotFoundError only when it actually sends a request. Tests without LLM calls pass.
  • Repeated requests. Identical requests are answered in the order they were recorded. When they run out, auto records a new one and replay repeats the last.
  • auto appends. New recordings are added to the existing file, so adding a step to an agent records only the new step.
  • record replaces. The old file is not loaded. After the run the file holds only this run's interactions.

On CI

- run: npm ci
- run: npm test
  env:
    ANTHROPIC_API_KEY: dummy   # SDKs need some key; replay never sends it

GitHub Actions and most CI services set CI=true, so tomiko runs in replay mode. A request without a recording fails the build and shows the closest recording, so a forgotten re-record can't call the paid API from CI.

Request matching

A live request matches a recording when all of these are equal:

  • the HTTP method;
  • the URL, after secret query parameters are redacted;
  • the body, compared as canonical JSON: object key order doesn't matter, array order does. Paths listed in ignore are removed first.

Headers are not compared and not stored.

Ignoring volatile fields: ignore

Leave out parts of the body that change between runs (ids, timestamps, cache markers). Paths are dot-separated, and * matches any key or array index:

configure({
  ignore: [
    "metadata.user_id",           // one field
    "messages.*.cache_control",   // the field in every message
    "tools.*.input_schema.description",
  ],
});

When nothing matches

In replay mode, a request with no recording throws RequestMismatchError. tomiko looks for the most similar recording for the same method and URL, preferring ones not yet used in this run, and prints a leaf-by-leaf diff:

RequestMismatchError: No recorded interaction in cassette "agent/booking" matches POST https://api.anthropic.com/v1/messages.
Closest recording (94% similar) differs in:
  ~ system: "…for a small restaurant. [-Always-]{+Never+} confirm the time and…"
  + temperature: 0.2
  - metadata.user_id: "u_123"

If the change is intentional, re-record with TOMIKO_MODE=record, or allow near matches with the `fuzzy` option.
MarkMeaning
~changed. For strings, only the changed words are shown, as [-old-]{+new+} with a few words of context.
+present in the live request only
-present in the recording only

Up to 12 differences are shown, and values are clipped at 120 characters. If nothing was ever recorded for that endpoint, the error says so instead.

Near matches: fuzzy

With fuzzy: 0.9, a request at least 90% similar to a recording replays it, and the diff becomes a warning in the report. This is useful while you iterate on prompt wording.

  • Similarity is computed per JSON leaf and weighted by length, so a one-word edit in a long prompt barely moves the score, while a changed model name or tool does.
  • Strings are compared word by word (a Dice coefficient over words).
  • A recording from a different model is never used, however similar the prompt.
  • The value must be in (0, 1], or false (the default) to turn it off.

Assertions

The matchers read the requests and responses the cassette served in this run, whether recorded or replayed. They work on any cassette: the one passed to your callback, currentCassette(), or one from openCassette().

expect(c).toHaveCalledTool("book_table", { guests: 2, table: expect.any(Number) });
expect(c).toHaveCalledToolTimes("search_tables", 1);
expect(c).toHaveCalledToolsInOrder(["search_tables", "book_table"]);
expect(c).not.toHaveCalledTool("cancel_booking");
expect(c).toHaveMadeRequests({ max: 5 });       // no runaway loops
expect(c).toHaveUsedModel(/claude-opus/);
expect(c).toCostLessThan(0.05);
expect(c).toHaveUsedFewerTokensThan(20_000);
MatcherPasses when
toHaveCalledTool(name, input?)the model called the tool at least once. With input, at least one call's arguments must contain it.
toHaveCalledToolTimes(name, n)the tool was called exactly n times
toHaveCalledToolsInOrder(names)the tools were called in this relative order; other calls may come in between
toHaveMadeRequests(n | { min, max })the number of requests is exactly n, or within the range (either bound optional)
toHaveUsedModel(model | RegExp)at least one request used this model
toCostLessThan(usd)the estimated cost is strictly below usd
toHaveUsedFewerTokensThan(n)input, output, cache read and cache write tokens add up to fewer than n

How input is compared

For toHaveCalledTool, the expected input is matched as a subset: every key you give must be in the arguments with a matching value, and nested plain objects are compared the same way. Other values, including arrays, use your runner's equality, so asymmetric matchers work:

expect(c).toHaveCalledTool("search", { query: expect.stringMatching(/lisbon/i) });
expect(c).toHaveCalledTool("book_table", { guest: { name: "Ana" } }); // other keys allowed
expect(c).toHaveCalledTool("tag", { labels: ["vip", "window"] });     // the array must be equal

Failure messages

When a tool matcher fails, it lists what the agent did instead, with arguments shortened to 80 characters:

expected cassette "booking.test.ts/books a table" to call tool "cancel_booking".
Tool calls:
  search_tables({"time":"19:00","guests":2})
  book_table({"table":12,"guests":2,"note":"window"})

What counts

  • Tool calls are read from Anthropic tool_use, server_tool_use and mcp_tool_use blocks, OpenAI Chat Completions tool_calls and Responses API function_call items, in both plain and streamed responses. Arguments streamed in fragments are reassembled.
  • Requests include every request the cassette handled: retries and requests hit by a fault count too.
  • toCostLessThan throws if a request has usage but no known price, instead of counting it as free. Add the model with the pricing option.

Custom assertions with c.calls

For anything the matchers don't cover, read the raw data. c.calls is a list of RecordedCall, one per request, in order. c.toolCalls is every tool call across them.

await useCassette(async (c) => {
  await agent.run("Table for two");

  const last = c.calls.at(-1)!;
  expect(last.text).toMatch(/booked/i);              // the final answer
  expect(last.requestBody.system).toContain("restaurant");
  expect(c.calls.every((call) => call.status === 200)).toBe(true);
  expect(c.toolCalls.map((t) => t.name)).toEqual(["search_tables", "book_table"]);
});

Failure injection

Live APIs rarely fail on cue. Faults let you test retry and error handling deterministically, on top of a normal recording:

import { fault } from "tomiko";

// 429, 429, then the recording
await useCassette(run, { faults: [fault.rateLimit({ times: 2 })] });

// the connection drops mid-stream
await useCassette(run, { faults: [fault.cutStream({ afterEvents: 3 })] });

A faulted request never reaches the network and is never recorded. Error responses use each provider's real format, so SDKs throw their usual typed errors (RateLimitError, InternalServerError, …) and retry as they would in production.

HTTP error faults send retry-after-ms and retry-after headers derived from retryAfterMs, so SDKs retry right away instead of waiting out a real backoff.

Choosing which requests fail

Every factory accepts targeting options (FaultTarget):

OptionEffect
timeshit the first times requests that when accepts. Default 1; Infinity hits all of them.
onrequest numbers to hit, 1-based: a number or an array. It counts every request the cassette handles in this run, retries and faulted requests included. Takes precedence over times.
when(request) => boolean. Only requests it accepts are hit. It receives { method, url, body }, with the URL redacted and the body parsed.
 
fault.serverError({ on: [1, 3] });                     // requests 1 and 3
fault.rateLimit({ times: Infinity });                   // every request
fault.overloaded({ when: (r) => r.body?.model === "claude-opus-5-5", times: 2 });
fault.networkError({ when: (r) => r.url.includes("/v1/messages") });

Combining faults

Pass several faults in the array. Each keeps its own hit count. On one request: latency delays add up and apply first; then the first failing fault (rateLimit, overloaded, serverError or networkError) in declaration order answers the request; cutStream applies to responses that are actually served.

Asserting on faults

Each RecordedCall has a fault field naming the fault that hit it ("rate_limit", "overloaded", "server_error", "network_error", "cut_stream" or "latency"). A network error has status: 0.

test("survives two rate limits in a row", async () => {
  await useCassette(
    async (c) => {
      const answer = await askWeather("Porto");
      expect(answer).toMatch(/sunny/i);
      expect(c.calls.filter((call) => call.fault === "rate_limit")).toHaveLength(2);
    },
    { faults: [fault.rateLimit({ times: 2 })] },
  );
});

test("gives up when the API stays overloaded", async () => {
  await useCassette(
    () => expect(askWeather("Porto")).rejects.toThrow(/overloaded/i),
    { faults: [fault.overloaded({ times: Infinity })] },
  );
});
✦

Faults work even without a cassette file: a faulted request is answered before tomiko looks for a recording. A test that only checks failure paths needs no recording at all.

Streaming

Responses with content-type: text/event-stream are recorded as a list of chunks, exactly as they arrived, and replayed chunk by chunk. stream(), finalMessage(), for await loops, streamText and streamed tool calls behave as they did live.

  • Recorded while you read. While recording, tomiko passes the stream through to your code and copies each chunk as it is read. Your code sees the same bytes in the same chunks.
  • Stopping early is fine. If your code stops reading (or never reads), the recording isn't cut short: close() drains the rest before saving.
  • Failed streams aren't saved. A stream that fails while recording would replay truncated, so it is left out of the cassette and a warning is added to the report.
  • Usage and tool calls are reassembled from the events: Anthropic message_start / message_delta / input_json_delta, OpenAI Chat delta.tool_calls, and the Responses API's final response.completed.

To test a stream that breaks mid-way, use fault.cutStream().

Cost & tokens

tomiko reads token usage from every response, streamed or not, and estimates the cost from a price table.

Usage

Usage is normalized across providers into four counters (Usage):

FieldAnthropicOpenAI
inputTokensinput_tokensprompt_tokens / input_tokens minus cached tokens
outputTokensoutput_tokenscompletion_tokens / output_tokens
cacheReadTokenscache_read_input_tokens*_tokens_details.cached_tokens
cacheWriteTokenscache_creation_input_tokens0

inputTokens always means uncached input. For streams, counters are cumulative across events, so tomiko keeps the largest value of each.

Prices

Prices are in USD per million tokens. Anthropic list prices are built in (defaultPricing). Add or override entries with the pricing option, which is merged over the built-in table:

configure({
  pricing: {
    "gpt-5": { input: 1.25, output: 10, cacheRead: 0.125 },
    "my-fine-tune": { input: 2, output: 8 },
  },
});
  • A key matches a model id exactly, or as a prefix, with the longest key winning: "claude-opus-5-5" also prices "claude-opus-5-5-20261001".
  • Bedrock's anthropic. prefix and Vertex's @version suffix are stripped before lookup.
  • cacheRead defaults to 10% of input, and cacheWrite to 125% of input.
  • A model with no price is reported in unpricedModels and is never counted as free: toCostLessThan throws on it.
⚠

Prices change. The built-in table reflects Anthropic list prices as of October 2026. Override them if you need exact figures, or if your account has different rates.

Printing a summary

Every cassette that served at least one request leaves a report. formatSummary() turns them into text:

import { afterAll } from "vitest";

  if (summary().cassettes > 0) console.log(formatSummary());

Security & redaction

Cassettes are meant to be committed, so tomiko keeps secrets out of them by default:

DataWhat is stored
Request headersNever stored. That includes x-api-key, authorization and cookies.
Response headersOnly content-type, retry-after, request-id and x-request-id.
URL query parametersValues of key, api_key / api-key / apikey, access_token, token, auth, sig and signature (any case) become REDACTED.
Request and response bodiesStored as is.

Scrubbing bodies: redact

Bodies hold whatever your prompts and the model's answers hold, which may include personal data. redact receives each interaction just before it is written and returns the version to save:

const EMAIL = /[\w.+-]+@[\w-]+\.[\w.]+/g;

configure({
  redact: (interaction) => {
    const scrub = (v: unknown) => JSON.parse(JSON.stringify(v).replace(EMAIL, "user@example.com"));
    interaction.request.body = scrub(interaction.request.body);
    interaction.response.body = scrub(interaction.response.body);
    return interaction;
  },
});
  • It receives a deep copy, so you can change it in place. Your test still sees the real values during this run.
  • It runs on every interaction in the file on each save, including ones recorded earlier, so it should give the same result when applied twice.
  • Redacted values are what later runs match against. If you rewrite something that's part of the request, replay will see a different body: prefer ignore for request fields that only need to be left out of matching.

Saving

  • A file is written only when the run recorded something new. Replaying never rewrites it.
  • Writes go to a temporary file and are then renamed, so an interrupted run never leaves a half-written cassette.
  • Loading checks version: 1; any other format throws TomikoError.
  • You can edit cassettes by hand, for example to shorten a long answer. Keep the request body as is, or the request won't match.
✦

Commit __cassettes__/. Re-record when you change a prompt, a tool or a model on purpose: TOMIKO_MODE=record npx vitest run -t "<test name>".

The viewer

npx tomiko view

Builds a single HTML page from your cassettes and opens it in the browser: each cassette as a conversation, with the system prompt, tools, tool calls and results, the response, and the tokens, cost and time of each step. The page needs no server, so you can attach it to a CI run as an artifact.

  • A sidebar lists every cassette with its request count, tokens and cost; filter it by path or model.
  • System prompts repeated from the previous request are collapsed, and so is conversation history already shown.
  • Raw request and response JSON are one click away.
  • Light and dark themes follow your system.

cassette() tomiko

cassette<T>(name: string, fn: (cassette: Cassette) => T | Promise<T>, options?: TomikoOptions): Promise<T>

Runs fn with globalThis.fetch routed through the named cassette, then saves any new recordings and resolves with what fn returned.

name string

Cassette name, relative to dir. Slashes create subdirectories; .json is added.

fn (cassette: Cassette) => T | Promise<T>

Your code. It receives the open Cassette, for assertions.

options optional TomikoOptions

Merged over the configure() defaults. See options.

  • Throws NestedCassetteError if another cassette is active.
  • fetch is restored even if fn throws. The cassette is closed either way, and if both fn and the save fail, the error from fn is the one thrown.
  • Clients that captured fetch before this call should use the exported fetch.

openCassette() tomiko

openCassette(name: string, options?: TomikoOptions): Promise<Cassette>

Opens a cassette without touching globals. Pass c.fetch to a client and call await c.close() when done, to save recordings and produce the report.

import Anthropic from "@anthropic-ai/sdk";
import { openCassette } from "tomiko";

const c = await openCassette("support/refund");
try {
  const client = new Anthropic({ fetch: c.fetch });
  await runAgent(client);
  expect(c).toHaveCalledTool("issue_refund");
} finally {
  await c.close();
}

Use it for concurrent work (each cassette has its own fetch, so several can be open at once), for long-lived clients, or when you don't want the global fetch patched.

configure() & resetConfig() tomiko

configure(options: TomikoOptions): void resetConfig(): void

configure sets defaults for every cassette opened afterwards. It's usually called once in a setup file. Calls accumulate: each one is merged over the previous defaults, and pricing tables are merged key by key. Options passed to a single cassette are merged over these defaults.

resetConfig clears all defaults.

configure({
  fuzzy: 0.95,
  ignore: ["metadata.user_id"],
  pricing: { "gpt-5": { input: 1.25, output: 10 } },
});

fetch tomiko

const fetch: typeof globalThis.fetch

A stable fetch that routes each call to whichever cassette is active at call time, and to the real network when none is. Hand it to clients created once at module load: new Anthropic({ fetch }). See Clients created before a test.

It is the same function tomiko installs as globalThis.fetch while a cassette is active. When no cassette is active, it calls the fetch that was global when tomiko loaded, so it never loops back into itself.

Errors tomiko

Every error tomiko throws extends TomikoError, and each error's name is its class name.

TomikoError

The base class. Also thrown directly for misuse: an unknown mode, a bad fuzzy value, an invalid cassette name, an unsupported file format, a request on a closed cassette, useCassette() outside a test, currentCassette() with none active, a matcher given something that isn't a cassette, or toCostLessThan on an unpriced model.

CassetteNotFoundError { file }

Replay mode, and the cassette file doesn't exist, and the test sent a request. Record it by running locally (auto) or with TOMIKO_MODE=record.

RequestMismatchError { method, url, cassette, diff, similarity }

Replay mode, and no recording matches the request. diff is the formatted difference from the closest recording and similarity its score (0..1); both are null if nothing was recorded for that method and URL.

NestedCassetteError

A cassette was activated while another was active. Cassettes don't nest.

import { RequestMismatchError } from "tomiko";

try {
  await cassette("agent", run, { mode: "replay" });
} catch (error) {
  if (error instanceof RequestMismatchError) console.log(error.similarity, error.diff);
  throw error;
}

Recipes

Guard against runaway agent loops

await useCassette(async (c) => {
  await agent.run("Book a table and email me the confirmation");
  expect(c).toHaveMadeRequests({ max: 6 });
  expect(c).toHaveCalledToolTimes("send_email", 1);
});

Put a budget on every test

import { afterEach, expect } from "vitest";
import { currentCassette, setupCassettes } from "tomiko/vitest";

setupCassettes();
afterEach(() => {
  expect(currentCassette()).toCostLessThan(0.10);
});

With Vitest's default sequence.hooks: "stack", after-hooks run in reverse order of registration, so this afterEach runs before the one from setupCassettes() closes the cassette.

Test a retry policy

test("retries once, then falls back to a smaller model", async () => {
  await useCassette(
    async (c) => {
      await agent.run("Summarize my inbox");
      expect(c).toHaveUsedModel("claude-haiku-5-5");
    },
    { faults: [fault.overloaded({ when: (r) => r.body?.model === "claude-opus-5-5", times: Infinity })] },
  );
});

Test a timeout without waiting

const client = new Anthropic({ timeout: 50, maxRetries: 0 });

await useCassette(
  () => expect(client.messages.create(params)).rejects.toThrow(/timed out/i),
  { faults: [fault.latency({ ms: 10_000 })] },
);

The simulated delay honours the request's abort signal, so the SDK's 50 ms timeout fires and the test finishes in 50 ms.

Record only LLM calls

const LLM_HOSTS = new Set(["api.anthropic.com", "api.openai.com"]);

configure({ intercept: (request) => LLM_HOSTS.has(new URL(request.url).hostname) });

Prompts with dates or random ids

A prompt that contains today's date never matches yesterday's recording. Either freeze the value in tests (vi.setSystemTime(), a fixed seed), or leave the field out of matching with ignore. If the value sits inside a long string, consider moving it into a separate field you can ignore.

Iterate on a prompt without re-recording each time

await useCassette(run, { fuzzy: 0.9 }); // small wording changes replay, with a warning

Once the wording settles, re-record with TOMIKO_MODE=record and remove fuzzy, so the cassette matches the final prompt exactly.

Compare models

for (const model of ["claude-opus-5-5", "claude-sonnet-5-5"]) {
  test(`books a table with ${model}`, async () => {
    await useCassette(async (c) => {
      await agent.run("Table for two", { model });
      expect(c).toHaveCalledTool("book_table");
      expect(c).toCostLessThan(0.05);
    });
  });
}

Each model gets its own cassette, so you can compare their behaviour, tokens and cost in npx tomiko view.

Troubleshooting

“Could not resolve authentication method”

The Anthropic SDK (and the OpenAI SDK, with its own message) throws this before sending the request when no API key is set, so tomiko never sees the request. When replaying, set any value: ANTHROPIC_API_KEY=dummy. The key is never stored and a replay never sends it.

Requests go to the real API instead of the cassette

The client captured fetch before the cassette was active, usually because it was created at module load. Pass fetch from tomiko: new Anthropic({ fetch }). See Clients created before a test.

CassetteNotFoundError on CI

The test sent a request, but its cassette was never recorded or never committed. Run the test locally once, then commit __cassettes__/. Check that .gitignore doesn't exclude it.

RequestMismatchError after changing a prompt

That's the point: the recording no longer reflects your code. The diff shows what changed. Re-record with TOMIKO_MODE=record, or allow near matches with fuzzy. If the difference is a volatile field (an id, a timestamp), add it to ignore.

NestedCassetteError

Two cassettes were active at once: useCassette() inside a test already covered by setupCassettes(), a cassette() inside another, or concurrent tests. Use one at a time, or openCassette() for concurrent work.

toCostLessThan throws “no price for …”

The model isn't in the price table. Add it: configure({ pricing: { "gpt-5": { input: 1.25, output: 10 } } }). tomiko refuses to count unknown models as free, so a budget can't pass by accident.

Recording works, but replay gives different results

Something else in your code is non-deterministic: the current time, random numbers, or unordered parallel requests. Two identical requests replay in recording order, but different requests sent in parallel may still race. Freeze time and seeds in tests, and look for parallel calls whose order differs between runs.

Matchers don't type-check

Import tomiko/vitest somewhere in the test (or the setup file) so the type augmentation loads. On Vitest older than 5, or on Jest, declare the types yourself: see Vitest and Jest.

Still stuck?

Open an issue on GitHub with the error and, if possible, the cassette. Check it for personal data first.

03 — Why tomiko

HTTP recorders capture bytes. tomiko reads the conversation.

nock and Polly don't know what a tool call is. tomiko knows it's looking at LLM traffic — and tests it that way.

event: message_startevent: content_block_startevent: content_block_deltaevent: content_block_stopevent: message_stop

Streams replay exactly

SSE comes back chunk by chunk, so stream(), finalMessage() and streamed tool calls behave as they did live.

search_tables→book_table

Assert behaviour, not strings

Which tools ran, with what arguments, in what order, how many requests it took — and what it cost.

Failures on demand

Rate limits, overloads, dropped connections and slow responses — in each provider's real error format.

04 — Failure paths

Live APIs rarely fail on cue.
Recordings do.

Inject a fault and the SDK throws its usual typed error, then retries right away instead of waiting out a real backoff. Pick one:

    test passed · your retry path works
    05 — When a prompt changes

    You'll know exactly what changed.

    In replay mode a request with no recording fails with the closest one and a word-level diff. Re-record on purpose, or allow near matches with fuzzy.

    ✗ weather.test.ts › answers with the weather tool
    RequestMismatchError: No recorded interaction in cassette
  "weather.test.ts/answers with the weather tool" matches
  POST https://api.anthropic.com/v1/messages.

Closest recording (90% similar) differs in:
  ~ messages[0].content: "…weather in Lisbon right now?now, in Celsius?"

If the change is intentional, re-record with TOMIKO_MODE=record,
or allow near matches with the fuzzy option.

    07 — Quick start

    Three lines to your first cassette.

    Wrap a test in useCassette. Run it once with a key. Commit __cassettes__/. That's the whole setup.

    1. Install npm i -D tomiko
    2. Record ANTHROPIC_API_KEY=… npx vitest
    3. Commit git add __cassettes__
